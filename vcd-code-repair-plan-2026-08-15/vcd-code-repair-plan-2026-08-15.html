03 P0 缺陷详解与修复指引（首批部署）

P0-1 · 成功句记账双记 + 费用双计 P0

位置：tts.ts:615-618（成功回调）+ queue-workers.ts:411-418（显式记账）

机制：v1.12.0 P0-B1 给 queue 主链补传 onApiCall（queue-workers.ts:293、L350），因此 tts.ts 成功路径 L615-618 触发一次 logApiCall（估算 0.0005 计费）；随后 queue-workers.ts:411-418 又显式 logApiCall 一次（按 realCostUsd 全额计费）——同一真实合成句 2 条日志 + 2 次费用累加；静音重合成成功路径更是 3 条。任务调用计数翻倍 → MAX_API_CALLS_PER_TASK=500（limits.ts:667）提前一半触发；tts.ts:613 注释"queue-workers 主链未传 onApiCall，无双记风险"已过时。

修复指引（二选一，推荐 a）
a. 删 queue-workers.ts:411-418 整块显式记账 — 保留 onApiCall 单点（L293/L350）；
   同时将真实费用信息并入回调：tts.ts:615 回调 opts 增加
   realCostUsd: (text.length) * getPriceTable(env).cosyvoicePerChar
   （env 可从 options.env 取，与 queue-workers 原口径一致）。
   → 成功句 1 条日志 + 1 次计费；CACHE_HIT 分支（L532-541 提前 return）天然不计费。
b. 反向：删除 tts.ts:615-618 成功回调，仅保留 queue-workers 显式记账 —
   但串行路径（tts.ts 直调方）将失去成功审计，不推荐。

P0-2 · 进度无条件 UPDATE 回退 P0

位置：queue-workers.ts:442；pipeline/utils.ts:95（重试路径）

机制：TTS 块消费者写 UPDATE tasks SET progress=? WHERE id=?——无单调守卫、无终态过滤。聚合超时强制 failed + 30s 宽限后 merge 已推进，晚到写完的块（56-65 区间）把 95/98 打回 ~60.5/58.25。此外 utils.ts:92-99：任务一旦 retry_count > 0，整个重试期走 allowRegression=true 无条件 UPDATE（双 isolate 并发可低值覆盖高值）。

修复指引
queue-workers.ts:442 改为：
  UPDATE tasks SET progress = ?, updated_at = datetime('now')
  WHERE id = ? AND progress < ? AND status NOT IN ('done','failed','cancelled')
  （bind rounded, taskId, rounded）— 与 utils.ts:98 单调守卫同款；
utils.ts:95 重试路径补同样守卫（不再 allowRegression=true 直写，
   仅在 retry 重置进度时由 pipeline-do.ts:557 显式归 0）。

P0-3 · strategy0r 用原始段时长 gate，未利用补长 P0

位置：ai/clone.ts:1408-1410

机制：seg0DurSec = (seg0.end - seg0.start) / 1000; if (seg0DurSec >= 3) —— 用原始 ASR 段时长判定，在调用 extractSeg 之前直接 skip。而 extractAudioSegmentUniversal（audio-dsp.ts:1530-1534）对 <3s 片段会自动补长到 3s。1.9s 段本可补长后尝试 enrollment（1 次付费），判定逻辑与提取的补长能力脱节——生产任务 2db01eb4 的 3 个说话人正是死在此处。

修复指引
删除 `if (seg0DurSec >= 3)` 前置 gate，改为：
  直接 extractSeg → 校验 wavBuffer 有效（byteLength > 1000 且非全静音）
  → deepPurifyWav → uploadToR2 → _cloneRetry（enrollment 自身会校验时长）。
  补长后仍不足 3s 的极端情况由 enrollment 侧拒绝，付费仍受
  paidEnrollCount ≤ 2 封顶（clone.ts:1180-1184）控制，无预算风险。

P0-4 · strategy4 "多参考融合"名存实亡（单 url） P0

位置：worker/clone.ts:82-91；ai/clone.ts:1446-1476

机制：CosyVoice enrollment 仅支持 单个 url 字段（v1.8.86 注释：原 audio 数组多参考是 Qwen-TTS 特性），selectedUrl = referenceAudioUrls[0]。strategy4 仍提取 Top3 段（3 次 extractSeg + 3 次净化 + 3 次 R2 上传），但只有第 1 段被使用——其余 2 段提取成本白烧；且注释（clone.ts:1437-1438"多参考融合可将相似度从 0.89 提升到 0.92+"）与实际行为不符，误导后续维护。

修复指引
方案 1（推荐，省成本）：strategy4 改为"逐段单次 enrollment、取首个成功"——
  按质量排序依次尝试，每段 1 次调用，成功即返回（paidEnrollCount≤2 封顶不变）；
  删除"收集 Top3 URL 一次性融合"的无效提取（省 2/3 提取开销）。
方案 2：若保留多参考意图，改为多次 enrollment 后选相似度最高结果（同方案1）。
同时修正 clone.ts:1437-1438 / clone.ts:82-91 注释，删除"0.89→0.92+"夸大表述。

P0-5 · 保底链无跨句合并补长（双路径能力不对齐） P0

位置：ai/clone.ts:1344-1350 vs pipeline/stage-clone.ts:21-48 / 995

机制：主路径具备完整融合能力（buildExtendedCloneAsr 短句合并 → scoreAllSegments 融合虚拟段 → selectOptimalSegmentGroup 智能合并 → shouldMergeSegments 拼接，总时长 ≥3s 即融合，v1.11.20）；而 lastResortClone 保底链直接用原始 ASR 段 allSpeakerSegs，无任何跨句合并。短句说话人在主路径失败后，保底链没有任何产生 ≥3s 参考的可能性。

修复指引
将 v1.11.20 融合门槛逻辑接入 lastResortClone：
  ① 入口复用 buildExtendedCloneAsr（同主路径），生成合并后段列表；
  ② 合并后总时长 ≥3s 的说话人，直接用合并段走 strategy0r（补长后判定，见 P0-3）；
  ③ 融合判定与主路径共用同一函数（scoreAllSegments/shouldMergeSegments），
     消除双路径能力差异（F3 闭环）。

P0-6 · 性别兜底被 null 门控挡死 P0

位置：pipeline/stage-speaker.ts:312-354

机制：if (unifiedResult) 门控包住整段"localGenders 兜底 + 落库"逻辑。DeepSeek fetch 抛异常返回 null（非 HTTP 失败）时，localGenders 已计算出 F0/时长兜底性别，但既不写 state.precomputedGenders 也不落库——v1.11.22 的兜底在 fetch 异常路径完全失效，TTS 端 gender 缺失 → hash 50/50 或默认女声 → "男女声错乱"。

修复指引
① 门控改为：`if (unifiedResult || Object.keys(localGenders).length > 0)`
   —— 兜底分支独立于 unifiedResult 存在；
② 落库增加写入后回读校验（SELECT 比对），失败时 pipeline_events 记
   speaker_genders_write_failed + err=（当前 catch 全吞错，无观测）；
③ 顺带修 emotion.ts:611-619 本地关键词推断优先于 DeepSeek 的问题
   （DeepSeek 返回正确性别会被本地误判覆盖）。

P0-7 · 语速口径分裂（引擎 1.3 vs 上游 1.5） P0

位置：tts-engines.ts:193（引擎钳 1.3）vs tts.ts:1035/1040（串行 1.5）vs elastic-correction.ts:112（MAX_SPEED 1.5）

机制：引擎最终钳位 MAX_RATE = 1.3，而上游按 1.5 计算请求——预期加速被静默压回 1.3，残余偏差压给 merge 硬截断；elastic-correction L2 直调 DashScope rate=1.5 则绕过引擎钳位（最坏 ×1.73）。elastic-correction.ts:714 注释宣称与 0.85/1.15 一致，常量已改 0.7/1.5，注释过期。

修复指引
① tts.ts:1035/1040 上限 1.5 → 1.3；elastic-correction.ts:112 MAX_SPEED → 1.3；
② 删除 elastic-correction.ts:714-719 过期注释，或同步为 0.7/1.3；
③ ja 估算统一单一 mora 口径（tts-engines.ts:253 moraRate=6.5 为权威，
   lang-rates.ts:97 safe=7.0 与 tts-engines.ts:225 注释 7.5 收敛到 6.5）。
