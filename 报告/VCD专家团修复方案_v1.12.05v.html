二、问题 1：全片女声 + 情感不足（TTS 音色链断连）

根因链（三层断点）

克隆成功写 speaker_tracks（spk_1 真实音色）→ DO 重启 state.voiceId 丢失→ orchestrator.ts:1100 无条件落 qwen_system→ queue-workers:350 任务级 OR 短路→ 所有句子 qwenSystemFallback→ resolveQwenVoiceId 确定性女声

关键证据：speaker_tracks 中 spk_1 有真实音色（克隆成功），但 TTS 块消息 voice=qwen_system（tts_error_full 事件实证），且 qwen_system+gender 缺失时 tts-engines.ts:177-181 回退 longanlingxi（女声）——即使 spk_1 标记 male 也因音色未消费而听不出。

#改动位置系统化理由

三、问题 2：句子时长"打假" + 首句被二句压上

根因链

  • 校验被打假：drift 检测读 seg.durationMs（stage-align.ts:218 已被 WSOLA 修正值覆盖）→ TTS 产物与目标槽的真实偏差从未检出；失败线（300ms/20%）宽于纠偏能力（15%）+ wsolaHeavy 豁免 → 校验形同虚设
  • 主动制造重叠：enableOverlapLayering=true（stage-merge.ts:1115）→ dsp-merge.ts:977-982 本段 PCM 可延伸至下一段的 endMs（非下一句起点），重叠区仅 2kHz 低通让位
  • 前端无保护：spliceByTimeline 按 startMs 硬放置、无 WSOLA 无校验，超长段后写覆盖先写
  • 历史教训回退：v5.9.52 移除"间隙借用"（因造成重叠），v1.10.87 以 800ms 地板形式恢复——同一链路两套方案并存（借用语义"不覆盖下一句" vs 分层语义"覆盖到下一句 endMs"互相矛盾）

系统修复方案（校验恢复 + 重叠收敛 + 句间保护）

#改动位置系统化理由
1TTS 段合成返回后立即比对"实际时长 vs ASR 槽长"，记录原始偏差（不被后续 WSOLA 覆盖）；drift 改用原始合成时长tts.ts / stage-align.ts恢复真实校验——"时长打假"的根本消除
2分层延伸上限从"下一段 endMs"收回到"下一段 startMs - 100ms"（与 parseSRT 100ms 间隙保护语义统一）dsp-merge.ts:977-982收敛重叠方案——不再两套并存，句间 100ms 间隙成为唯一语义
3merge 层目标槽上限 nextStartMs - 100ms；溢出优先找停顿点截断而非延伸dsp-merge.ts:925句间保护下沉到拼接层（前端/后端同语义）
4drift 不合格走"按段 WSOLA 修正 + 复核"闭环，替代"宽失败线 + RETRY 重合成"（省 API、不打假）stage-align.ts:255-328校验与重试解耦——修正优于重跑
需要决策：分层模式（enableOverlapLayering）是收回上限（方案 2，保留分层能力但限定不越下一句）还是直接关闭（最保守，零重叠风险但可能丢失"自然过渡"听感）？专家团建议收回上限——保留分层的人声自然性，同时用 100ms 间隙保证不压台词。

四、问题 3：背景音声音小

根因链

  • 前端下载路径系数偏低：audio-synth.ts:149-175 bgmGain 默认 0.35（-9.1dB），人声帧 duck 至最低 0.15（-16.5dB）——而后端混音默认 -2dB（0.79x）。同一任务前后端听感不一致（双方案并存，前端是下载实际听到的路径）
  • >50MB 长视频断连：v1.12.4e C2 守卫（stage-merge.ts:1384-1394）跳过后端 BGM 混音，仅纯人声 + 独立 BGM 轨 → 前端若未正确混入则背景音缺失/极小
  • 三处调用参数不一致：多段混音走 RMS 自动匹配（-2~-6dB），单段/块级混音用默认 -2dB，未走自动匹配

已被绕过的最佳方案：v1.11.28 曾删除 SKIP_BACKEND_BGM_MIX 开关（生产 SKIP=true 曾致无背景音），现已恒执行——但 50MB 守卫仍是事实上的"禁用"；FFmpeg loudnorm 因 DO 128MB OOM 永久禁用（stage-merge.ts:8-11），由 JS normalizeLoudness 接管（替代方案已在运行）。

系统修复方案（系数统一 + 大文件块级混音全量覆盖）

#改动位置系统化理由
1前端 mixVoiceWithBgm bgmGain 与后端对齐（0.5-0.6 起步，duck 下限 0.25 而非 0.15）audio-synth.ts:149-175消除前后端听感不一致（前端是下载实际路径）
2>50MB 大文件改为块级混音全量覆盖（复用已有 L1445-1495 块级混音，删除"跳过"分支）stage-merge.ts:1384-1394复用已有能力，不再"断连"
3单段/块级路径补传 duckingOptions（复用 L1537-1570 的 RMS 自动匹配）stage-merge.ts:1460/1771三处调用参数收敛一致

五、问题 4：10% 卡顿（ASR 轮询空转）

现状与根因

10% 的组成 = 分离（本次 103s，正常）+ ASR 服务端耗时 + 轮询感知。ASR 提交成功后进入纯轮询空转（DO alarm → 单次轮询 → setAlarm），CPU/时间片完全闲置。

已实现的优秀方案（确认在运行）：分离∥ASR 提前提交（v1.10.69/v1.12.04d，分离返回即用火山临时 URL 提前提交 ASR）、回调模式前 8 轮 2s 高频探测、长视频 VAD 8 路并发。这些是本任务 10% 只花 ~2.5 分钟的原因。

系统修复方案（复用已有并行骨架，不新增模块）

#改动位置系统化理由
1预算预检（checkPreExecutionBudget）移入 B 波，与克隆/翻译并行执行（依赖 ASR 完成后即可，不依赖 B 波结果）orchestrator.ts B 波B 波已有三路并发骨架，第四路成本极低
2预设音色场景在 ASR 轮询期间真正启动克隆 enrollment（复用 stage-extract.ts:1362-1395 缓存预热点，当前只查缓存不调用）stage-extract.ts复用既有预热钩子，把"只查缓存"升级为"预热+注册"

说明：10% 卡顿的主因是 ASR 服务端耗时（不可控），进度感知已在批次二修复（每轮心跳平滑）。并行化是锦上添花，非根因修复。

六、问题 5：55% 卡顿（B 波状态断连）

根因链（时间线完全吻合 5min33s）

B 波三路 allSettled 完成（12:50:18）→ 合并尾段（落库/flags/进度）无 io-timeout → 挂起 ~333s→ speaker 步骤 360s 超时（Promise.race）→ abort → bWaveDone 内存标记未持久化（断连窗口）→ 重入 D1 恢复（v1.10.71）→ 克隆降级场景恢复不命中 → B 波重跑（重复克隆+翻译）

九、决策点确认记录（用户已定稿）

  1. 分层模式：确认"收回上限到下一句 startMs - 100ms"——即恢复源程序既有"槽内 WSOLA 伸缩 + 100ms 间隙"语义；不关闭分层（保留自然过渡，关闭会影响句子意思）。
  2. BGM 系数：不采用静态系数——复用源程序 v1.12.02/R3 双向 RMS 自动匹配（BGM 输出 ≈ 语音 -2dB ≈ 80% 音量，随语音音量动态调节），前端与后端同算法。
  3. 修复顺序：以质量为主——批次 A → B → 批次三前端 → C → D。
  4. 克隆 prefix 修复：确认并入批次 A（与音色链同链路、一次回归、一行改动风险极低）。
  5. 批次三：确认统一安排，按"后端音色+时长 → BGM+B 波 → 前端四阶段 → 音库 → SRT → 清理"分批提交验证。
