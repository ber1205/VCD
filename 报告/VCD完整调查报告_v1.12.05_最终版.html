三个最关键的机制级缺陷：

缺陷 A · 语言对翻译策略被取行 bug 丢弃（stage-translate.ts:1288-1289）

缺陷 B · SRT 说话人判断恒为 true（stage-asr.ts:287-310）

SRT 解析后 speaker_id 先被硬编码为 'spk_0'（truthy），随后 srtHasSpeakers 判断恒为 true → diarization-only ASR 永不调用，上传 SRT 的任务永远单说话人。

缺陷 C · F0 性别"覆盖 DeepSeek"是假象（stage-speaker.ts:348-454）

注释声称 F0 直判覆盖 DeepSeek，但 persistGenders 键级合并只补缺失（DeepSeek 先落库），F0 实际只"填空"不"覆盖"；且 F0 依赖声学提取成功（16/24-bit WAV + YIN ≥2 帧 + 句长 ≥2s），任一不满足即静默跳过 → 落入"时长兜底"（dur≥8s?male:female）→ 短句碎片恒判女声。

4背景音是否保留到最后合成

结论：正常路径下 BGM 会被保留并混入最终 dubbed_audio.wav；但存在多条"静默跳过 BGM 混音"的守卫路径，任一命中即成片无背景音。

混音真实存在（stage-merge.ts）：

L1354  入口守卫: if (state.bgmR2Key)
L1497  读取 BGM: env.MEDIA_BUCKET.get(state.bgmR2Key)
L1571  实际混音: mixPcmWithDucking(voiceBufferForMix, bgmBuffer, duckingOptions)
L1581  覆盖写回 dubbed_audio.wav

BGM 混音被跳过的守卫路径（任一命中 → 无背景音）：

守卫后果
bgmR2Key 为空（分离 API 未返回伴奏 URL / 下载失败）跳过混音
人声轨 >50MB跳过后端混音，保留纯人声 + 独立 BGM 轨（前端可合成）
BGM R2 对象不存在跳过混音
mixPcmWithDucking 返回 null（位深/解析失败）跳过混音
BGM 非 RIFF（AAC）→ 强制转码失败混音失败

历史根因（代码注释实证）

  • v1.11.99d（P0）：ensureWavTrack 里 parseVolcengineApiKey(env) 传参错误（误传整个 env 对象）→ trim() TypeError → BGM 恒 AAC → merge 解析失败 → 成片无背景音（已修）。
  • v1.10.82：ON CONFLICT(task_id, code) 子句恒抛错 → bgm_track 产物从未落库（已修）。
  • v1.10.64 F11：DO 重启后 bgmR2Key 丢失 → 已通过 tasks 表恢复修复。

实测：sintel 05a（8fc75d11）BGM 混音成功（bgm_mixed_ok: voice=4984844B bgm=8810906B mixed=4984844B）；任务 6a69e28f 因分离超时无 BGM。

5音视频合成在哪里进行

结论：Worker 端不产出真实 MP4。dubbed_audio.wav 是纯音频 WAV；最终 MP4 由前端在用户点击下载时用浏览器 FFmpeg.wasm 实时合成。

证据：

  • ffmpeg-wasm-integration.ts:141-153：burnSubtitles 是恒空 stub（"FFmpeg 硬烧录已禁用 (DO 内存保护), 视频由前端合成"）。
  • stage-merge.ts:2059-2067：软 mux 已禁用（CF Workers 运行时无 DOM/Worker 构造器，FFmpeg.wasm 0.12 API 必然 "Worker is not defined"）。
  • muxDubbedVideo / extractAudio 已定义但全库零调用（死代码）。
  • 前端 client.tsx:1926-2033：下载时浏览器合成 —— 音频 synthesizeDubbedAudio()（含 BGM 混音），视频 -c:v copy -c:a aac 秒级 remux。
这是正确的架构决策：视频封装完全委托浏览器按需合成，不消耗 Cloudflare CPU 配额（符合"5 分钟 CPU"约束）。

7F0 性别区分 + DeepSeek 兜底

结论：F0 声学分析确实存在（male<155Hz / female≥175Hz，灰区 155-175Hz 交 DeepSeek），但存在 3 个机制缺口，导致实际效果与设计不符。

两阶段判断逻辑（stage-speaker.ts:326-400）：

// F0 直判（仅 ≥2s 句）
if (meanF0 < 155) out[spk] = 'male';
else if (meanF0 >= 175) out[spk] = 'female';
else grayZoneSpks.add(spk);          // 155-175Hz 灰区 → 交 DeepSeek

// 时长兜底（F0 无数据时）
out[spk] = dur >= 8000 ? 'male' : 'female';   // ← 短句碎片恒判女声

三个机制缺口

缺口 1 · F0"覆盖"DeepSeek 是假象

stage-speaker.ts:348-351 注释声称"F0 明确区间直判覆盖 DeepSeek 语义"，但落库顺序是 DeepSeek 先（L488）、local 后（L495），且 persistGenders 只补缺失键（L454 if (!merged[k]) merged[k]=v）。DeepSeek 已判的说话人，F0 永远不会覆盖它。

缺口 2 · F0 可达性脆弱

F0 逻辑被包在 if (deepseekKey && ...) 内（L68）；且依赖 extractAcousticFeaturesForSentences 成功（音频可下载 + 16/24-bit WAV + YIN 检出 ≥2 帧 + 句长 ≥2s）。任一不满足 → f0BySpk 为空 → F0 静默跳过 → 落入时长兜底。

缺口 3 · SRT 任务 F0 完全跳过

SRT 任务 audioUrlForAcoustic = null（L93）→ 声学提取跳过 → 性别仅靠"时长≥8s→男"兜底，多角色 SRT 配音性别大概率错乱。

8情感来源与传递

结论：TTS 用的情感来自 DeepSeek unified 分析（roleEmotionAnalysis.emotions），不是 ASR 输出；情感参数确实传入 TTS API 请求体（instruction + volume + SSML），但存在 2 个缺口。

传递链路（完整）：

DeepSeek unified 逐句情感→ stage-tts.ts:892 块消息 emotion/intensity→ queue-workers.ts:402 callQwenTTS→ tts-engines.ts:658 buildCosyVoice3Instruction→ WS 请求体 instruction/volume/SSML

两个缺口

缺口 1 · ASR 基线情感是死数据

asr.ts:184 提取 emotion 字段（emotion_recognition_enabled: true 多花的模型能力），但全链路无消费者。TTS 情感 100% 依赖 DeepSeek —— DeepSeek 未标注的句子回退全局"平静专业"。

缺口 2 · SRT 任务情感恒为默认

SRT 任务跳过 unified 分析 → roleEmotionAnalysis 为空 → 所有句子情感回退"平静专业"。

强度表达局限：intensityToVolume 只有弱/中/强 3 档映射到音量（tts-engines.ts:409-418），CosyVoice 对 instruction 的遵循程度是质量瓶颈。

根因 4 · 覆盖率校验只认精确相等

effectiveDubbingCoverage 仅把 src.trim() === t.trim() 判为无效，近似源语言的译文被计为有效。

21.2 成本测算（VCD 母带处理场景）

场景：每任务 1 次母带混音（侧链压限 + EBU R128 + 交叉淡化），标准实例 0.5 vCPU / 1 GiB，ffmpeg 处理约 30-60s：

单任务成本:
  vCPU: 0.5 × 45s × $0.000020 = $0.00045
  内存: 1 GiB × 45s × $0.0000025 = $0.0001125
  单任务 ≈ $0.00056
$5 内含 22,500 vCPU-s → 可承载 22,500 / (0.5×45) ≈ 1000 个任务/月免费
按 200min 长视频任务 (处理 5-10 分钟): 22,500 / (0.5×420) ≈ 107 个任务/月免费

结论：VCD 早期用户量（每月几十~几百任务）在 $5 计划内零额外成本。对比：不用 Containers 则需自研 Rust WASM 实现 EBU R128/侧链压限/交叉淡化，工程量数周~数月，且质量难以对齐 ffmpeg 成熟滤镜。

21.4 成本保护设计（重点）

  1. 月度 vCPU 预算熔断：复用现有保险丝机制 —— 增加 CONTAINER_MONTHLY_VCPU_S_LIMIT（如 20,000 vCPU-s ≈ $5 内含 89%，留 10% 余量），超限自动切回 WASM 降级路径，并告警。
  2. 任务级容器计时器：每任务容器执行秒数上限（如 15 分钟），超限终止并落诊断事件（防死循环/恶意长任务）。
  3. 并发闸门：复用 global-tts-limiter 模式，容器任务并发上限（如 2-3 个），防止突发峰值同时唤醒多个实例。
  4. 成本记账：每次容器调用记 cost_audit_log（api_name='container_ffmpeg'），与现有 cost-monitor 面板同源可查。
  5. 冷启动优化：sleepAfter 设 10 分钟（非无限保活），平衡"复热延迟"与"闲置计费"；批量任务可预唤醒一个实例。
  6. 出口限制：容器只写 R2（内网，无出口费），不对外直出（1TB 内含够用，但仍需记账监控）。

22网站安全审计与加固方案

22.1 P0 高危（资金/提权，必须优先修）

P0-1 · 兑换码熵源不安全（shared.ts:977）

Math.random() 生成 16 位兑换码（V8 xorshift128+，可预测），兑换码 = 金钱，可被批量爆破。修法：改 crypto.getRandomValues。

P0-2 · 超级管理员 = 用户名判定 + 开放注册 + 硬编码回退（shared.ts:747-749）

isSuperIerTMT = username === (SUPER_ADMIN_USERNAME || 'ierTMT')，与 role 无关；SUPER_ADMIN_USERNAME 未配置时回退字面量 'ierTMT'，而注册接口（auth.ts:316-371）不保留该用户名 → 新部署或未配 env 时，任何人注册 ierTMT 即获得全部超管权限（跑迁移/重置任意密码/发卡）。修法：改用 role 判定 + env 必须配置 + 注册黑名单。

P0-3 · 火山 webhook 无验签（index.ts:648-719）

v1.12.04b 故意移除 HMAC 验签（仅数字 task_id 校验）→ 未认证可写任意 R2 键 volcengine_callbacks/{id} + 唤醒任意任务 DO。修法：恢复 HMAC 验签（参考 ASR 回调 index.ts:1085-1128 的成熟实现）。
