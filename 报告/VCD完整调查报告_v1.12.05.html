本次调查对 VCD 配音 pipeline 进行了全链路代码审计（6 个并行调查代理覆盖 20+ 核心文件）与 D1 生产库实证（任务 6a69e28f 及 sintel 系列测试任务）。核心结论：主链路（分离→ASR→翻译→TTS→混音→前端合成）整体通畅，但存在 3 个机制级代码缺陷和若干链路缺口，它们共同造成了用户观察到的"全员集合说出中文、译文混源语言、全女声无男声、衔接生硬、无背景音乐"等问题。

三个最关键的机制级缺陷：

缺陷 A · 语言对翻译策略被取行 bug 丢弃（stage-translate.ts:1288-1289）

unified 主路径用 .slice(1,2) 从 buildLocalizationPrompt 取行，只拿到"配音要求"行，28 个语言对策略 + 14 个目标语言策略全部失效。zh→ja 的"读音保真"规则（译文必须含假名，严禁纯汉字句）因此未注入 → "全員、集合！"纯汉字 → TTS 按中文发音。

缺陷 B · SRT 说话人判断恒为 true（stage-asr.ts:287-310）

SRT 解析后 speaker_id 先被硬编码为 'spk_0'（truthy），随后 srtHasSpeakers 判断恒为 true → diarization-only ASR 永不调用，上传 SRT 的任务永远单说话人。

缺陷 C · F0 性别"覆盖 DeepSeek"是假象（stage-speaker.ts:348-454）

注释声称 F0 直判覆盖 DeepSeek，但 persistGenders 键级合并只补缺失（DeepSeek 先落库），F0 实际只"填空"不"覆盖"；且 F0 依赖声学提取成功（16/24-bit WAV + YIN ≥2 帧 + 句长 ≥2s），任一不满足即静默跳过 → 落入"时长兜底"（dur≥8s?male:female）→ 短句碎片恒判女声。

此外，测试数据揭示了两个关键实证：① 任务 6a69e28f（CN→JP test.mp4）火山分离 API 轮询超时（300s/85 次）→ 无人声无 BGM → 克隆降级 qwen_system → 全部句子用系统音色 + 纯汉字译文按中文发音；② sintel 系列 05a→05b 之间出现性别检测回归（05a 正确识别男女，05b-05d 全部判为女声）。

3人声/背景音分离（火山引擎）

结论：使用火山引擎 MediaKit separate-voice API，单次调用返回人声 + 伴奏双轨，链路正常。

分离调用链：stage-extract.ts:616 → volcengineSeparateVoice(audioUrl, key, timeout, env, undefined, true, costMeta)（第 6 参 true = 请求伴奏轨）→ ai/volcengine.ts:511 volcengineSubmitAndPoll('separate-voice', ...)。

双轨产物 R2 key：

人声：audio/{taskId}/voice.wav
伴奏：audio/{taskId}/bgm.wav
缓存：cache/vocalsep/{hash}.voice.wav + .bgm.wav

降级链（与旧文档不同）：

separate-voice 直接分离→ 失败重试 1 次→ 轮询超时标记降级→ FFmpeg WASM 兜底（v1.11.99c 已移除）→ 克隆走降级链 / BGM 缺失

实测异常（任务 6a69e28f，CN→JP test.mp4）

extract_audio / volc_poll_timeout:
  task=amk-tool-separate-voice-751498035458 轮询超时 300000ms (85次), 返回 null 交上层降级
extract_audio / vocal_sep_no_ffmpeg:
  分离未产出 vocal (sepErr=N/A), 跳过 FFmpeg 兜底, 克隆走降级链

该任务 vocal_flac_r2_key 与 bgm_flac_r2_key 均为 null → 无 BGM、克隆降级。这是"没有背景音乐"的直接根因（本次任务）。

4背景音是否保留到最后合成

结论：正常路径下 BGM 会被保留并混入最终 dubbed_audio.wav；但存在多条"静默跳过 BGM 混音"的守卫路径，任一命中即成片无背景音。

混音真实存在（stage-merge.ts）：

L1354  入口守卫: if (state.bgmR2Key)
L1497  读取 BGM: env.MEDIA_BUCKET.get(state.bgmR2Key)
L1571  实际混音: mixPcmWithDucking(voiceBufferForMix, bgmBuffer, duckingOptions)
L1581  覆盖写回 dubbed_audio.wav

BGM 混音被跳过的守卫路径（任一命中 → 无背景音）：

守卫后果
bgmR2Key 为空（分离 API 未返回伴奏 URL / 下载失败）跳过混音
人声轨 >50MB跳过后端混音，保留纯人声 + 独立 BGM 轨（前端可合成）
BGM R2 对象不存在跳过混音
mixPcmWithDucking 返回 null（位深/解析失败）跳过混音
BGM 非 RIFF（AAC）→ 强制转码失败混音失败

历史根因（代码注释实证）

  • v1.11.99d（P0）：ensureWavTrack 里 parseVolcengineApiKey(env) 传参错误（误传整个 env 对象）→ trim() TypeError → BGM 恒 AAC → merge 解析失败 → 成片无背景音（已修）。
  • v1.10.82：ON CONFLICT(task_id, code) 子句恒抛错 → bgm_track 产物从未落库（已修）。
  • v1.10.64 F11：DO 重启后 bgmR2Key 丢失 → 已通过 tasks 表恢复修复。

实测：sintel 05a（8fc75d11）BGM 混音成功（bgm_mixed_ok: voice=4984844B bgm=8810906B mixed=4984844B）；任务 6a69e28f 因分离超时无 BGM。

5音视频合成在哪里进行

结论：Worker 端不产出真实 MP4。dubbed_audio.wav 是纯音频 WAV；最终 MP4 由前端在用户点击下载时用浏览器 FFmpeg.wasm 实时合成。

证据：

  • ffmpeg-wasm-integration.ts:141-153：burnSubtitles 是恒空 stub（"FFmpeg 硬烧录已禁用 (DO 内存保护), 视频由前端合成"）。
  • stage-merge.ts:2059-2067：软 mux 已禁用（CF Workers 运行时无 DOM/Worker 构造器，FFmpeg.wasm 0.12 API 必然 "Worker is not defined"）。
  • muxDubbedVideo / extractAudio 已定义但全库零调用（死代码）。
  • 前端 client.tsx:1926-2033：下载时浏览器合成 —— 音频 synthesizeDubbedAudio()（含 BGM 混音），视频 -c:v copy -c:a aac 秒级 remux。
这是正确的架构决策：视频封装完全委托浏览器按需合成，不消耗 Cloudflare CPU 配额（符合"5 分钟 CPU"约束）。

6字幕/时间轴/说话人分离

结论：ASR 使用 qwen-audio-3.0-asr-flash-filetrans，开启说话人分离 + 情感识别，输出 speaker_id + 字幕 + 毫秒时间轴，链路正常。
asr.ts:65-73   parameters = { diarization_enabled: true, emotion_recognition_enabled: true, ... }
asr.ts:111     model: 'qwen-audio-3.0-asr-flash-filetrans'
asr.ts:184     提取 emotion 字段（但下游无人消费 —— 见 §8）

说话人分离在 ASR 阶段完成（callQwenASRDiarizationOnly），speaker_diarize 步骤做统计 + 两路 DeepSeek + 本地评分。上传 SRT 时：

  • SRT 输入路径：跳过 ASR 文字识别，直接用上传字幕和时间轴（stage-asr.ts:258）。
  • SRT 增强路径（video+SRT）：SRT 文本/时间戳绝对优先，仅从 ASR 取 speaker_id。

7F0 性别区分 + DeepSeek 兜底

结论：F0 声学分析确实存在（male<155Hz / female≥175Hz，灰区 155-175Hz 交 DeepSeek），但存在 3 个机制缺口，导致实际效果与设计不符。

两阶段判断逻辑（stage-speaker.ts:326-400）：

// F0 直判（仅 ≥2s 句）
if (meanF0 < 155) out[spk] = 'male';
else if (meanF0 >= 175) out[spk] = 'female';
else grayZoneSpks.add(spk);          // 155-175Hz 灰区 → 交 DeepSeek

// 时长兜底（F0 无数据时）
out[spk] = dur >= 8000 ? 'male' : 'female';   // ← 短句碎片恒判女声

三个机制缺口

缺口 1 · F0"覆盖"DeepSeek 是假象

stage-speaker.ts:348-351 注释声称"F0 明确区间直判覆盖 DeepSeek 语义"，但落库顺序是 DeepSeek 先（L488）、local 后（L495），且 persistGenders 只补缺失键（L454 if (!merged[k]) merged[k]=v）。DeepSeek 已判的说话人，F0 永远不会覆盖它。

缺口 2 · F0 可达性脆弱

F0 逻辑被包在 if (deepseekKey && ...) 内（L68）；且依赖 extractAcousticFeaturesForSentences 成功（音频可下载 + 16/24-bit WAV + YIN 检出 ≥2 帧 + 句长 ≥2s）。任一不满足 → f0BySpk 为空 → F0 静默跳过 → 落入时长兜底。

缺口 3 · SRT 任务 F0 完全跳过

SRT 任务 audioUrlForAcoustic = null（L93）→ 声学提取跳过 → 性别仅靠"时长≥8s→男"兜底，多角色 SRT 配音性别大概率错乱。

8情感来源与传递

结论：TTS 用的情感来自 DeepSeek unified 分析（roleEmotionAnalysis.emotions），不是 ASR 输出；情感参数确实传入 TTS API 请求体（instruction + volume + SSML），但存在 2 个缺口。

传递链路（完整）：

DeepSeek unified 逐句情感→ stage-tts.ts:892 块消息 emotion/intensity→ queue-workers.ts:402 callQwenTTS→ tts-engines.ts:658 buildCosyVoice3Instruction→ WS 请求体 instruction/volume/SSML

两个缺口

缺口 1 · ASR 基线情感是死数据

asr.ts:184 提取 emotion 字段（emotion_recognition_enabled: true 多花的模型能力），但全链路无消费者。TTS 情感 100% 依赖 DeepSeek —— DeepSeek 未标注的句子回退全局"平静专业"。

缺口 2 · SRT 任务情感恒为默认

SRT 任务跳过 unified 分析 → roleEmotionAnalysis 为空 → 所有句子情感回退"平静专业"。

强度表达局限：intensityToVolume 只有弱/中/强 3 档映射到音量（tts-engines.ts:409-418），CosyVoice 对 instruction 的遵循程度是质量瓶颈。

注释自称"注入压缩版(target-only 指令)"，但实现取错了行。结果：全部 28 个语言对策略 + 14 个目标语言策略在主路径全部失效，unified prompt 里只剩通用一句"译文须像母语者口语, 非翻译腔"。旧路径（unified 失败降级 stepTranslate）才用完整策略。

11.2 翻译自检（prompt 层摆设）

unified prompt 是"翻译+自检+情感标记+音节精算+时长预算"五合一，输出 schema 含 quality_pass/quality_notes/overall_quality，但这些字段全库无读取方。真正的质量门是 stage-align 的漂移检测（基于音频时间轴漂移，而非模型自评）。

11.3 "译文出现源语言"根因链

根因 1 · unified prompt 无"禁止输出源语言"指令

v1.10.86 主动删除了"语言保真"规则（该规则让 DeepSeek 把源语言专有名词原样保留），但没补上等价的"禁止输出源语言"正向指令。

根因 2 · zh-ja"读音保真"规则未注入主路径（缺陷 A）

"译文必须含平假名或片假名,严禁纯汉字句"规则被 .slice(1,2) 丢弃 → 模型输出纯汉字"全員、集合！" → TTS 按中文发音。这正是"全员集合说出中文"的直接机制。

根因 3 · 语言守卫只拦精确相等

TTS 前检查 译文 === 原文 才抛错（orchestrator.ts:1177-1204）；"全員集合"→"全员集合"（标点/汉字差异）不满足 ===，直接放行进 TTS。

根因 4 · 覆盖率校验只认精确相等

effectiveDubbingCoverage 仅把 src.trim() === t.trim() 判为无效，近似源语言的译文被计为有效。

11.4 翻译记忆库与术语表（机制完整）

  • TM 记忆库：lookupTranslationMemory（source_hash 精确命中 + Levenshtein 0.90 语义匹配，跨用户共享），isMemoryTargetValid 防污染（译文=源文或非目标语言脚本则跳过）。
  • 术语表：用户术语表 CRUD + DeepSeek 动态术语 + 领域术语库，注入 unified prompt（"术语表硬锁"），但仅当 glossaryTerms.length > 0 才注入。

12SRT 上传 vs 无 SRT

结论：程序设计上，上传 SRT 是"文本/时间轴质量提升 + 分析链路降级"的混合体。对纯翻译/校对是提升；对配音是性别/角色维度降级。
环节无 SRT（视频）上传 SRT
ASR 文字识别✅ 完整❌ 跳过（用上传字幕）
ASR 纠错✅❌ 跳过（用户文本优先）
unified 分析（角色/性别/情感/语境）✅❌ 跳过
F0 声学性别✅❌ 跳过（仅时长兜底）
说话人 diarization✅ ASR 自带⚠️ 恒跳过（缺陷 B）
文本/时间轴准确性ASR 估计✅ 用户人工（更高）

时间轴优先：上传 SRT 的时间轴在 SRT 输入路径中绝对优先（stage-asr.ts:1165-1180），贯穿翻译、TTS 槽位、音频合并、字幕产物。质量门对 SRT 任务无差异化逻辑，但 SRT 时间轴更准 → 漂移更小 → 更容易通过。

关键结论

  • 上传 SRT 的文本和时间轴质量确实更高（用户人工校对），且省 ASR/克隆费用（字幕输入免 ASR 和克隆费）。
  • 但角色/性别/情感/语境系统性缺失：SRT 任务无 unified 分析、无 F0，性别仅靠"时长≥8s→男"兜底 → 多角色 SRT 配音性别大概率错乱。
  • 机制级缺陷 B 使 SRT 任务永远单说话人（diarization 永不调用）。

14.1 10% 卡顿（asr_processing）

18机制级优化建议

遵循"机制级根治 + 代码收敛"哲学，以下建议均为统一机制而非挂点补丁：

18.1 翻译链路（P0）

  1. 修复取行 bug：buildLocalizationPrompt 改为返回结构化对象（原则/配音要求/语言对策略/配音适配），unified prompt 注入完整语言对策略，而非 .slice(1,2) 猜行。
  2. 补"禁止输出源语言"正向指令：unified prompt 显式声明"指定目标语言则全部输出该语言，禁止保留任何源语言文字；专有名词按目标语习惯音译"。
  3. 语言守卫升级：从"精确相等"升级为"Unicode 脚本比例检测"（译文主要脚本 ≠ 目标语言脚本 → 拦截重译），覆盖"全員集合"这类近似源语言。
  4. 自检结果接入质量门：quality_pass/overall_quality 从"摆设"变为质量门输入（与漂移检测联合决策）。

18.2 性别链路（P0）

  1. F0 改为真覆盖：合并顺序改为"F0 明确区间优先，DeepSeek 仅填空/灰区"，并让 state.precomputedGenders 保存合并结果而非最后来源。
  2. F0 可达性加固：声学提取失败时落诊断事件（非静默跳过），并保留 DeepSeek 兜底路径。
  3. 时长兜底去性别化：dur≥8s?male:female 改为"无信号时按 voiceId 稳定 hash 50/50 分配"（与 tts-engines.ts:212-232 对齐），避免短句碎片恒判女声。

18.3 SRT 链路（P0）

  1. 修复 srtHasSpeakers 恒 true：判断应基于 SRT 原始文本中的说话人标记（解析 <i>/{spk_}），而非已硬编码的字段。
  2. parseSRT 支持说话人标记解析：识别 <i>Speaker1</i> / {spk_0} 并映射为 speaker_id。
  3. SRT 任务补性别/情感：SRT 无说话人标记时调用 diarization-only ASR 补说话人；SRT 任务保留 F0（用 vocal 轨）或至少保留 DeepSeek 性别推断。

18.4 声音衔接（P1）

  1. 段间真交叉淡化：非重叠段之间引入 10-20ms 等功率重叠 crossfade（而非"淡出至 0 + 淡入"静音桥接）。
  2. 淡入淡出加长：8ms → 20-30ms 线性/余弦淡化，消除 click。
  3. WSOLA 上限放宽：拉伸上限 1.05 → 1.15（与压缩对称），减少硬切。
  4. 静音兜底段加过渡：silence:// 段与语音段边界加 5ms 交叉淡化。

18.5 进度体验（P1）

  1. 统一长步骤心跳：ASR/翻译/TTS/WSOLA 全部接入 startProgressHeartbeat（10s），消除 10%/55%/72% 静默窗口。
  2. 批级进度写入粒度对齐：ASR 每 5 轮写一次 → 每轮写（配合等值跳过 + 节流，D1 开销可控）。
  3. SSE 插值与 D1 权威值收敛：72 的 SSE 插值应与 D1 实际进度一致，避免"前端 72 后端 65"的跳变。

18.6 克隆/引擎（P1）

  1. 预留多引擎切换架构：preferredCloneEngine 从字面量改为枚举 + 路由层（cosyvoice3 / indextts25 / qwen），为 IndexTTS-2.5 预留接口（符合流程图设计）。
  2. 分离超时重试降级：separate-voice 300s 超时后增加"重试一次 + 降级保 vocal"策略，避免直接放弃 vocal 导致连锁降级。
  3. 克隆参考段提取加固：05b 的 strategy4_failed 无可用段 说明参考段提取失败率高，需诊断事件 + 多段拼接兜底。

18.7 人工校对（P2，暂不启用）

  1. 恢复为可配置只需改 2 处（§13），建议将 ENABLE_MANUAL_REVIEW 改为 env 变量驱动（而非硬编码常量）。
  2. 前端灰调状态保留，后端放行逻辑不变 —— 当前设计已满足"整体通畅、暂时不运行"。

21Cloudflare Containers 引入评估（成本控制）

结论：Containers 值得引入，仅用于重型音频处理（母带混音/EBU R128 响度/侧链压限）；关键发现是 Workers Paid $5 本身已包含 375 vCPU-min/月 的 Containers 额度，对 VCD 当前用量（每月几十到几百任务）完全可以在 $5 内零额外成本运行。必须配套消费保护设计。

21.1 关键事实：Containers 并非"完全独立计费"

计量单价（超量）Workers Paid $5 内含
vCPU$0.000020 / vCPU-s375 vCPU-min/月（= 22,500 vCPU-s）
内存$0.0000025 / GiB-s25 GiB-hrs/月
磁盘$0.00000007 / GB-s200 GB-hrs/月
出口（NA/EU）$0.025 / GB1 TB/月

Containers 于 2026-04-13 GA，按 10ms 活跃切片计费，闲置只付内存+磁盘；单实例上限 4 vCPU / 12 GiB / 20 GB 磁盘；无 GPU、无持久盘、无自动伸缩；冷启动 1-3 秒[6][7]。

21.2 成本测算（VCD 母带处理场景）

场景：每任务 1 次母带混音（侧链压限 + EBU R128 + 交叉淡化），标准实例 0.5 vCPU / 1 GiB，ffmpeg 处理约 30-60s：

单任务成本:
  vCPU: 0.5 × 45s × $0.000020 = $0.00045
  内存: 1 GiB × 45s × $0.0000025 = $0.0001125
  单任务 ≈ $0.00056
$5 内含 22,500 vCPU-s → 可承载 22,500 / (0.5×45) ≈ 1000 个任务/月免费
按 200min 长视频任务 (处理 5-10 分钟): 22,500 / (0.5×420) ≈ 107 个任务/月免费

结论：VCD 早期用户量（每月几十~几百任务）在 $5 计划内零额外成本。对比：不用 Containers 则需自研 Rust WASM 实现 EBU R128/侧链压限/交叉淡化，工程量数周~数月，且质量难以对齐 ffmpeg 成熟滤镜。

21.3 与 Rust WASM 自研对比

维度Rust WASM（Worker 内）Containers（ffmpeg）
工程量自研 EBU R128/侧链/WSOLA 全套，数周-数月Dockerfile + ffmpeg 命令，数天
质量需逐项验证对齐标准（响度/压限精度风险）ffmpeg 成熟滤镜（loudnorm/sidechaincompress），行业标准
CPU 配额消耗 Worker CPU（5min/请求上限，长视频 5-10min 处理会击穿）不占 Worker CPU 配额（10ms 切片独立计费）
成本$0（含在 $5）$5 内含额度内 $0；超出按量（见 21.4 保护）
内存128MB 限制（此前 FFmpeg.wasm 在 DO 内 OOM 的根因）单实例 12 GiB
策略建议：双路径并存——Containers 为主（高质量、省人力），Rust WASM 保留为降级路径（Containers 不可用/超预算时 fallback），避免"断线"即全瘫。符合"机制级根治 + 接线复用"哲学。

21.4 成本保护设计（重点）

  1. 月度 vCPU 预算熔断：复用现有保险丝机制 —— 增加 CONTAINER_MONTHLY_VCPU_S_LIMIT（如 20,000 vCPU-s ≈ $5 内含 89%，留 10% 余量），超限自动切回 WASM 降级路径，并告警。
  2. 任务级容器计时器：每任务容器执行秒数上限（如 15 分钟），超限终止并落诊断事件（防死循环/恶意长任务）。
  3. 并发闸门：复用 global-tts-limiter 模式，容器任务并发上限（如 2-3 个），防止突发峰值同时唤醒多个实例。
  4. 成本记账：每次容器调用记 cost_audit_log（api_name='container_ffmpeg'），与现有 cost-monitor 面板同源可查。
  5. 冷启动优化：sleepAfter 设 10 分钟（非无限保活），平衡"复热延迟"与"闲置计费"；批量任务可预唤醒一个实例。
  6. 出口限制：容器只写 R2（内网，无出口费），不对外直出（1TB 内含够用，但仍需记账监控）。

22网站安全审计与加固方案

结论：基础安全面扎实（JWT/PBKDF2/参数化查询/CORS/魔数校验均正确），但存在 3 个 P0 高危（资金/提权）与 6 个 P1 风险，其中"兑换码 Math.random 熵源"与"超管=用户名判定 + 开放注册"是必须优先修复的资金级漏洞。

22.1 P0 高危（资金/提权，必须优先修）

P0-1 · 兑换码熵源不安全（shared.ts:977）

Math.random() 生成 16 位兑换码（V8 xorshift128+，可预测），兑换码 = 金钱，可被批量爆破。修法：改 crypto.getRandomValues。

P0-2 · 超级管理员 = 用户名判定 + 开放注册 + 硬编码回退（shared.ts:747-749）

isSuperIerTMT = username === (SUPER_ADMIN_USERNAME || 'ierTMT')，与 role 无关；SUPER_ADMIN_USERNAME 未配置时回退字面量 'ierTMT'，而注册接口（auth.ts:316-371）不保留该用户名 → 新部署或未配 env 时，任何人注册 ierTMT 即获得全部超管权限（跑迁移/重置任意密码/发卡）。修法：改用 role 判定 + env 必须配置 + 注册黑名单。

P0-3 · 火山 webhook 无验签（index.ts:648-719）

v1.12.04b 故意移除 HMAC 验签（仅数字 task_id 校验）→ 未认证可写任意 R2 键 volcengine_callbacks/{id} + 唤醒任意任务 DO。修法：恢复 HMAC 验签（参考 ASR 回调 index.ts:1085-1128 的成熟实现）。

22.3 P2 加固项与"已确认安全"清单

P2 加固项

  • JWT 无吊销/轮换（auth.ts:467-488）：旧 refresh token 7 天内持续有效 → 增加版本号吊销或缩短有效期。
  • UploadSessionDO 无鉴权绑定（upload-session-do.ts）：UUID 即凭证 → 绑定 user_id。
  • CORS *.pages.dev 通配（shared.ts:523-533）+ X-Admin-Key 非恒定时间比较（index.ts:828-836）。
  • WS ?token= URL 传参（index.ts:992）：可能入日志 → 已提供 ticket 方案缓解，推广使用。

已确认安全（无需改动）

  • JWT HMAC-SHA256 + 常量时间比较 + exp 校验；PBKDF2 100k 迭代 + 16 字节盐；bcrypt 老哈希向后兼容静默升级。
  • JWT_SECRET 无硬编码回退（缺失即抛错）。
  • SQL 全参数化（仅 3 处白名单内插）；无 SSRF 面（fetch 目标均为固定域名）；无路径遍历。
  • D1 原子限流 UPSERT（rate-limit.ts:47-72）；上传 MIME 白名单 + 魔数双重校验 + 分片首片魔数。
  • CORS 精确白名单（非 pages.dev 部分）；无 token/密码落日志。

19结论

总体判断：程序主体流畅完整，架构设计达到较高水准，但距离"顶级克隆翻译配音"存在 3 个机制级缺陷（A/B/C）和若干链路缺口。

  • 分离/混音/合成链路：火山分离正常、BGM 正常路径保留混音、视频前端合成 —— 架构正确；本次"无 BGM"是分离超时偶发，非设计缺陷。
  • 翻译链路：语言对策略设计地道但主路径失效（缺陷 A），是"译文不地道 + 源语言混入 + 纯汉字中文发音"的总根因。
  • 性别链路：F0 存在但"只填空不覆盖"（缺陷 C）+ 时长兜底恒判女声，是"全女声无男声"的核心机制。
  • SRT 链路：文本/时间轴质量提升正确，但说话人恒单（缺陷 B）+ 角色/性别/情感缺失。
  • 情感/克隆：情感确实传入 TTS（instruction+volume+SSML），但 ASR 情感死数据 + 克隆质量受参考段/跨语言限制。
  • 卡顿：10%/55%/72% 是"长步骤无中间进度 + D1 写入降频"的同一类问题，应机制级统一解决。

以上为只读调查结论，未修改任何代码。等待用户命令后按 P0→P1→P2 顺序实施修复。
